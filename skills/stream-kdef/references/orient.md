## Step 0 — orient (once per conversation)

1. Call `fantasy-football-mcp-server:ff_get_status`. Note `server.tool_contract`, `capabilities.write` (all false in this version), `league.current_week`, `league.edit_key`, the `season` and `schedule` blocks (below), and every `sources[]` row whose `freshness` is `stale`, `expired`, `never_loaded`, `unreadable` or `not_published`, or whose `last_error` or `backoff_until` is set. A `stale` source is still used, with its age (name it under Confidence & freshness). An `expired` source (past its hard limit), a `never_loaded` one, or an `unreadable` one (the file its last refresh recorded is missing or damaged) cannot be relied on: a tool that needs it answers `STALE_ONLY` or leaves that input out and names it. Name the source to the user and ask them to run `ff refresh all` in a terminal (or `ff refresh` with that row's `id`; `ff refresh weather` for a weather row); `ff doctor` says what is wrong. A `not_published` source is upstream's state, not a fault: the NFL season in progress has no file of that kind upstream yet (injuries before the first report, stats before week 1). Say so, answer with what the tools return (they name the missing input), and never ask the user to run `ff refresh` for it — nothing changes until upstream publishes, and the server checks again on its own. A `backoff_until` means the data provider asked the server to wait: give the time and do not ask for a refresh before it.
   - **Version check.** If `server.tool_contract` differs from this Skill's `metadata.tool_contract`, stop and say: "These Skills expect tool contract N but the server reports M — install the Skills and the server from the same release, then ask again." Do not continue with mismatched tools.
   - **Season.** `season.nfl_season`, `season.phase` (`preseason`, `regular`, `postseason`, `offseason`), `season.week`, `season.league_season`, `season.league_matches`. When `league_matches` is `false`, the league file is for another season than the NFL season in progress: say so before any advice, and offer the `onboard` Skill's new-season step ("set up my new season") — it changes nothing without the user's confirmation. When `phase` is `offseason`, the season is over: retrospective questions still work; lineup advice waits for the next schedule. `season.reference_past_vintage[]` names a reference table (`venues`, `flex_rules`, `analytics_base_rates`) last verified for an earlier season: name it under Confidence & freshness. `season.week_bound_exceeded: true` means the published schedule has weeks past 22, which the tools cannot be asked about yet: say so if the user asks about one.
   - **Schedule.** `schedule.recent_changes[]` lists kickoff changes the server detected in the last 14 days (`game` such as `CHI@BUF`, `week`, `kind`, `old` → `new`); `schedule.tentative_weeks[]` lists weeks whose kickoff times may still move (`placeholder_week`: the NFL has not set the times yet; `flex_window`: games may still be flexed until `until`; `tbd_time`: a game has a date but no time). A change or a tentative week that touches the user's players changes the deadline: see the guardrails. `schedule.calendar: "fallback"` means the server has no usable schedule (`fallback_reason`): lock times may be missing — ask the user to run `ff doctor`.
2. Read the league settings **once**: the `ff://league/settings` resource if the client offers it, otherwise `fantasy-football-mcp-server:ff_get_league`. Note `current_week`, `edit_key`, `weekly_deadline`, `rules.uses_faab`, `rules.faab_budget`, `rules.playoffs.start_week`, the roster slots, and `scoring.settings_hash`.
3. **No league yet.** A `NOT_FOUND` error whose hint starts "No league configured" means the user has no league file: say so and offer to set one up (the `onboard` Skill — "set up my league"). An `INTERNAL` error whose hint names `league.yaml` means the file exists but is unsafe or invalid: ask the user to run `ff doctor` in a terminal and fix exactly what it names. Never ask them to paste the file into the chat to debug it.

### Fresh at answer time

Every data tool first checks its NFL data against upstream and waits a few seconds for a newer release (about 6 s; up to 15 s when the data it needs is missing or past its hard limit). `meta.refresh` is present only when a check ran; its `sources[]` rows carry an `outcome`:

- `updated` or `revalidated` — the answer uses the newest release; nothing to say.
- `in_progress` — the refresh was still running when the answer was given: the warning names the release the answer used. When the decision is close (a coin flip, or a lock within the hour), say so and ask the same question again about a minute later — once; that re-ask is allowed by the re-fetch rules below.
- `failed`, `backoff`, `throttled` — the answer uses the stored release, named in the warning with its age. Repeat the warning; do not retry in a loop. A warning that says to restart the client means the installed `ff` was upgraded under the running server: ask the user to restart the client. Code `spawn` with a `next_retry_at` is a passing limit of the machine (the server tries again then); without one — or when `ff_get_status` `checks[]` shows `on_demand` not ok (`disabled_spawn`, `disabled_version`) — answers are no longer re-checked until the client restarts: say so.
- `joined`, `skipped` — another refresh was running, or none was needed.

`STALE_ONLY` carries a reason in its message: a refresh still running (retryable — ask once more a minute later), a refresh that failed (the hint names the code; `ff refresh <source>` in a terminal shows why, `ff doctor` says what is wrong), or a season upstream has not published yet (upstream's state — never suggest `ff refresh` for it).

### Never re-fetch within a conversation (plan 07 §5.3)

| Data | Rule |
|---|---|
| `ff_get_status` | once per conversation; again only after an error that mentions auth or provisioning |
| `ff_get_league` / `ff://league/settings` | once per conversation (24 h; an unchanged `settings_hash` means nothing changed) |
| `ff_get_roster` | once per hour per team; again after a `PRECONDITION_CHANGED`, or in `start-sit`'s game-day branch (at most once with `force_refresh: true`) |
| `ff_get_scoreboard` | once per hour before games; on every call in `start-sit`'s game-day branch (the server's 60 s cache absorbs repeats) |
| `ff_project_players` | once per (player set, horizon, week) — results are deterministic for a `seed` and a `settings_hash` |
| `ff_get_schedule`, `ff_get_injuries` | once per conversation unless the result's `meta.freshness` was `stale` |
| `ff_analyze_*` | re-run only when an input changed (a new roster, a new injury, a kickoff change) — `data.inputs[]` says which inputs were used and how old they were |
| after `meta.refresh` `in_progress`, or a retryable `STALE_ONLY` | the same call once more, about a minute later, when the decision is close |
| any tool | a result already in the conversation with `meta.age_s` under its class TTL is reused verbatim |

### What this version reads (the manual league)

- League settings and the user's roster come from the user's own private file `<config>/league.yaml`, which they keep up to date by hand. It is as current as their last edit: when the roster in it looks out of date, ask before recommending.
- NFL data — schedules, betting lines (implied totals), injuries, weekly rosters, player stat lines — comes from nflverse; game weather from Open-Meteo or the National Weather Service. The season, its weeks and its game days come from the published NFL schedule, so every season works the same way.
- Only what the user entered: the scoreboard shows the opponent entered for that week in the league file's `opponents:`, without scores (a week with no entry returns `matchups: []` — say a win probability needs that week's opponent in the file, and repeat any warning), and `ff_list_transactions` returns the transactions listed in the league file (often none).
- Not available, and never implied: a live free-agent pool (kicker/defense rankings are availability-blind, `availability: "unknown"`), other teams' rosters unless the user entered them, standings (empty, with a warning), game-day inactive lists, and the platform's own fantasy points (`match: null`).
