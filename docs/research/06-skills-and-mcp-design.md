## The answer in one paragraph

Put every deterministic computation and every data access in **tools** (≈28 core tools; annotated; compact text plus `structuredContent`), put every repeatable expert procedure in **Skills** (14 of them, one per decision type plus onboarding, retrospective and the write protocol), expose each Skill's entry point as an MCP **prompt** for clients that lack Skills, and serve slow-changing reference data (league settings digest, stat-id map, tool-output cheat-sheet, recommendation-log entries) as **resources**. For confirmation before any roster change, use a **two-step `prepare_* → commit_*` tool pair with a single-use token bound to the previewed diff and to a roster-state hash** as the base mechanism (it works in every client and is the only mechanism that binds *what was previewed* to *what is committed*), and layer **form-mode elicitation inside `commit_*` where the client advertises it** (Claude Code does; Claude Desktop does not, as of today). Ship server + Skills as one Claude Code **plugin** whose repo is its own marketplace, with the `skills/` directory copy-installable for everything else.

## A. The mechanisms, precisely

### A.1 Tools — schema, annotations, structured output, errors, pagination, and what clients do with them

**Spec revision.** The current MCP specification revision is **2026-07-28** (sitemap lists 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25, 2026-07-28, draft) [V https://modelcontextprotocol.io/sitemap.xml]. The TypeScript SDK **v2 implements 2026-07-28** [V https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/README.md]. 2026-07-28 changed the plumbing a great deal but not the shape of a tool: it removed protocol sessions and the `initialize` handshake (every request carries protocol version + client capabilities in `_meta`), added `server/discover`, replaced server-initiated requests with **Multi Round-Trip Requests (MRTR)**, made `resultType` mandatory on every result, moved tasks to an extension, deprecated Roots/Sampling/Logging, and loosened `inputSchema`/`outputSchema` to any JSON Schema 2020-12 [V https://modelcontextprotocol.io/specification/2026-07-28/changelog]. Design consequence for us: **no per-connection state** — anything that must survive across calls (a confirmation token, a draft board) is "an ordinary string in a tool result and an ordinary argument to subsequent tool calls", validated by the server on every call, opaque, with a stated lifetime and an expiry error the model can recover from [V spec tools page, "Stateful Tools"].

**Tool definition** [V https://modelcontextprotocol.io/specification/2026-07-28/server/tools]:

| Field | Rule |
|---|---|
| `name` | 1–128 chars, `[A-Za-z0-9_.-]`, case-sensitive, unique per server. Aggregating clients may prefix with a server id — so a service prefix in our own names (`yahoo_`, `nfl_`) is still worth it (mcp-builder best practices; Anthropic "writing tools" post) |
| `title` | display name — **mandatory for the Anthropic Directory** [V-local `tool-design.md`] |
| `description` | "the contract": what it does, what it returns, what it does *not* do; must not instruct Claude how to behave ("always do X") — that is treated as prompt injection at Directory review [V-local `tool-design.md`] |
| `inputSchema` | JSON Schema (2020-12 default); for no-arg tools use `{ "type": "object", "additionalProperties": false }` |
| `outputSchema` | optional; if present the server **MUST** return conforming `structuredContent` and clients **SHOULD** validate |
| `annotations` | `readOnlyHint` (default false), `destructiveHint` (default true), `idempotentHint` (default false), `openWorldHint` (default true) [V spec schema; defaults unchanged since 2025-06-18]. "Clients MUST consider tool annotations to be untrusted unless they come from trusted servers" — they are UX hints, never a security boundary |
| `icons`, `_meta` | optional; Claude Code reads `_meta["anthropic/maxResultSizeChars"]` to raise a tool's output cap (see below) |

**Result shape.** `content[]` (text/image/audio/`resource_link`/embedded resource) plus optional `structuredContent` (any JSON conforming to `outputSchema`); "a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block" [V tools page]. `tools/list` now carries `ttlMs` and `cacheScope` and **SHOULD be returned in a deterministic order** because it "improves LLM prompt cache hit rates" [V changelog minor 3, 5].

**Errors** — two classes, and the distinction matters for Skills [V tools page]: *protocol errors* (unknown tool, malformed request → JSON-RPC error, "models are less likely to be able to fix") and *tool execution errors* (`isError: true` in the result, "actionable feedback that language models can use to self-correct and retry"). "Clients SHOULD provide tool execution errors to language models." So: Yahoo 999/401/lock/IR-ineligible → `isError` with the next step in the text ("player locked at 13:00 ET; re-run `lineup_optimize` with `exclude_locked: true`"), never a raw upstream body (02 §4 mistake 6). The SDK returns invalid arguments as an `isError` result without running the handler [V TS SDK docs/servers/tools.md].

**Pagination** is cursor-based and applies only to the four `*/list` operations; page size is server-chosen; cursors are opaque and must not be persisted across sessions [V https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/pagination]. **Tool results are not paginated by the protocol** — a list tool paginates through its own arguments. Yahoo's player collection pages at 25 (03 §B.2), so `yahoo_get_players` takes `page_cursor` (opaque, encodes `start`) and returns `has_more`/`next_cursor` per the mcp-builder pagination guidance.

**What clients do with tools.** Claude Code: prompts for permission before MCP tool calls in standard permission modes; shows annotations in the `/mcp` panel; warns when a tool output exceeds **10,000 tokens** and truncates at **25,000** by default (`MAX_MCP_OUTPUT_TOKENS`; per-tool `_meta["anthropic/maxResultSizeChars"]` up to 500,000 chars; an oversize text result is saved to a file and replaced by its path); loads MCP tool schemas lazily through **Tool Search by default** [V https://code.claude.com/docs/en/mcp]. Anthropic Directory review makes `readOnlyHint`, `destructiveHint` and `title` **pass/fail**, requires **read and write operations in separate tools** ("a single tool accepting both GET and POST … is rejected"), and requires tools with free-form endpoints to cite the API docs [V-local `tool-design.md`]. Whether Claude Code auto-approves `readOnlyHint: true` tools without a prompt: [U-1].

### A.2 Elicitation — what the spec says, who supports it, and the comparison with a two-step tool

**The mechanism (2026-07-28)** [V https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation]:
- Two modes. **Form mode**: server sends `message` + `requestedSchema` (a *flat* object of `string`/`number`/`integer`/`boolean`/enum — single-select via `enum` or `oneOf {const,title}`, multi-select via an `array` of enum items — with optional `default`s); the client renders a native form; the user's answer comes back as `{action: "accept"|"decline"|"cancel", content?}`. **URL mode**: server sends a `url` + `message`; the client shows the full URL, gets consent, opens it in the user's browser; the interaction happens out of band and the client is not told the outcome.
- Delivery under MRTR: the server answers the *original* `tools/call` with `resultType: "input_required"`, an `inputRequests` map keyed by an id, and an opaque `requestState`; the client re-issues the same `tools/call` (new JSON-RPC id) with `inputResponses` and the echoed `requestState`. "Elicitations do not require that the server maintain state about users." The pre-2026 `notifications/elicitation/complete` and `elicitationId` were removed.
- Capability: clients declare `_meta.io.modelcontextprotocol/clientCapabilities.elicitation: { form: {}, url: {} }` on **each request**; an empty object means form only; "Servers MUST NOT send elicitation requests with modes that are not supported by the client."
- Security: "Servers MUST NOT use form mode elicitation to request sensitive information such as passwords, API keys, access tokens, or payment credentials"; "Servers MUST bind elicitation requests to the client and user identity"; clients "MUST provide UI that makes it clear which server is requesting information" and "MUST show the full URL to the user" in URL mode.
- SDK: `ctx.mcpReq.elicitInput({...})`; "only works against a client that declared the elicitation capability — per mode"; otherwise it "throws before anything reaches the wire, and the thrown message comes back as an ordinary `isError` tool result" ("Client does not support form elicitation.") [V https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/servers/elicitation.md]. The official `build-mcp-server` skill's canonical pattern is therefore: check `getClientCapabilities()?.elicitation` first, and fall back to a text result that asks the model to relay the question [V-local `references/elicitation.md`].

**Client support today (the decision-critical fact).**

| Client | Elicitation | Evidence |
|---|---|---|
| **Claude Code** | **Yes**, form + URL. Declares `elicitation: {form: {}, url: {}}` on 2026-07-28 connections; renders a dialog; an `Elicitation` hook can auto-respond (so an "accept" may come from a user-configured hook rather than a live human) | [V https://code.claude.com/docs/en/mcp "Respond to MCP elicitation requests"; changelog: "Added MCP elicitation support … (form fields or browser URL)" and "Added MCP URL-mode elicitation on 2026-07-28 protocol connections"; the official skill dates form+url to v2.1.76] |
| **Claude Desktop** | **No.** Feature request anthropics/claude-code#41110 (opened 2026-03-30, "Claude Code CLI supports MCP elicitation … but the Claude Desktop app does not") was closed `invalid` (out of scope for that repo) with no maintainer response; the official `build-mcp-server` skill lists Desktop as "Unconfirmed — likely not yet or very recent"; the MCP site's client matrix page now covers only extensions (Apps, auth, Skills-over-MCP) and shows Desktop with Apps only | [V issue; V-local `elicitation.md`; V https://modelcontextprotocol.io/extensions/client-matrix] |
| **claude.ai (web)** | Unknown/"Unknown" in the official skill; Apps only in the extension matrix | [V-local; V] |
| **Agent SDK** | Claude Code in print/SDK mode had an elicitation auto-cancel bug fixed in the changelog, which implies it is exercised there; not tested here | [V changelog line; U-8] |

So: **elicitation is a Claude-Code-only guarantee for this product's first users, and even there a hook can answer it.** It cannot be the sole gate.

**The alternative: a two-step tool pair with a bound token.** `prepare_<write>` computes the change, validates it against Yahoo's rules (slot eligibility, lock, IR eligibility, roster limits — 03 §C.1, 05 §14.1–14.2), writes a **journal row** and returns (a) a compact human-readable diff and (b) an opaque **confirmation token**. `commit_<write>` takes *only* the token. The binding, which the brief asks to be explicit:

- the token is 128 bits from a CSPRNG, stored server-side as the key of the journal row; the row holds the tool name, the league/team key, the **canonical serialized action** (the exact roster slot map or transaction XML that will be sent), a **hash of the roster/transactions state the preview was computed from**, the preview text, `created_at`, a TTL (10 minutes — inside Yahoo's 60-s freshness window several times over, short enough that a lock cannot pass unnoticed), and `used_at`;
- `commit_*` re-reads the live Yahoo state, recomputes the state hash and refuses with an `isError` ("stale: roster changed since preview at 13:02 ET — run `prepare_*` again") if it differs; refuses expired or already-used tokens; marks the row used **before** sending (journal-then-send, never auto-retried — 02 §3.11); and returns the Yahoo transaction key plus a reconcile-later note;
- the model cannot forge a token (it never sees the secret, and a random id has no structure to guess), cannot alter the action (the action is not an argument of `commit_*`), and a prompt injected into news text cannot substitute a different player because the only committable thing is what was previewed.

**What the two-step pair does *not* do:** prove that a human said yes. The model holds both halves and could call `commit_*` immediately. The human is put in the loop by the *client* (Claude Code's per-tool permission prompt, in standard permission modes) and by *elicitation* where available — which is exactly why the recommendation is layered:

| Layer | Mechanism | Guarantees | Available in |
|---|---|---|---|
| 0 (server, always) | `prepare_* → commit_*` with bound single-use token, staleness check, journal | committed action == previewed action; no drift, no injected substitution, no double-send; audit trail | every client |
| 1 (client) | `commit_*` annotated `readOnlyHint:false, destructiveHint:true, idempotentHint:true, openWorldHint:true`; description says "irreversible on Yahoo; only after the user has confirmed the preview" | the client's own confirmation prompt fires (Claude Code standard modes; org per-tool `ask`) | Claude Code (not in `bypassPermissions`/auto); other clients per their own policy |
| 2 (server, capability-gated) | inside `commit_*`, if the client declares `elicitation.form`, send a form elicitation whose `message` is the preview diff and whose schema is `{confirm: boolean}` (+ `faab_bid: integer` when relevant); execute only on `accept && confirm`; on `decline`/`cancel` return "not applied" | a client-rendered dialog the model cannot fabricate (subject to the user's own hooks) | Claude Code today; Desktop/claude.ai when they ship it — the SDK capability check makes this automatic |
| 3 (Skill) | the `roster-change-execution` Skill is the only Skill allowed to call `commit_*`; it pastes the preview to the user and waits for an explicit yes in chat; news text is data | consistency of behaviour; cheap | every Claude client that loads the Skill |

URL-mode elicitation to a local approval page (the pattern `HamCops/dodi` implements out of band with a one-shot per-proposal token) is a possible Layer 2b for clients with `url` but not `form`; it is not recommended for v1 because the spec requires the server to verify that the user who opens the URL is the user who started the request, which is unsolved for a local stdio process without a browser session.

**Given Yahoo's read-only reality**, the write tools are registered **only when the stored token's granted scope includes write** (`tools/list` "MAY vary by the authorization presented on the request" [V tools page]); a read-only install never lists them, and `roster-change-execution` degrades to printing the exact manual steps in Yahoo's UI vocabulary (03 §C.1 slot names). `notifications/tools/list_changed` is sent after a re-auth that changes scope — but note the prompt-cache cost in A.5.

### A.3 Resources and prompts — what each is good for, concretely

**Resources** are "application-driven, with host applications determining how to incorporate context" [V https://modelcontextprotocol.io/specification/2025-06-18/server/resources; the 2026-07-28 changes only move subscriptions to `subscriptions/listen`]. A resource is *read*, not *called*: `uri`, `name`, `title`, `description`, `mimeType`, `size`, annotations `audience` (`user`/`assistant`), `priority` (0–1), `lastModified`; templates are RFC 6570 with argument completion. **Clients do not auto-load them.** Claude Code exposes resources through `@server:scheme://path` mentions ("automatically fetched and included as attachments when referenced") *and* "automatically provides tools to list and read MCP resources when servers support them" — so in Claude Code the model can pull a resource on its own [V https://code.claude.com/docs/en/mcp "Use MCP resources"]. Claude Desktop's resource picker UI was not verified this session [U-3]. The official guidance: a resource beats a tool for "large reference data (docs, schemas, configs) that Claude should be able to browse" and "anything where 'Claude decides to fetch' is the wrong mental model"; a tool is better when there are side effects or parameters [V-local `resources-and-prompts.md`].

Concrete uses here (all read-only, all also reachable as a tool so no client is stranded):

| URI | Content | Why a resource |
|---|---|---|
| `yahoo-ff://league/{league_key}/settings` | the normalized settings digest: `S` (stat modifiers + bonuses), `R` (slots with eligibility), `N`, waiver/FAAB/trade/playoff scalars, `edit_key`, `weekly_deadline` | changes once a season; ~1k tokens normalized vs several k raw; every Skill's step 0 reads it once |
| `yahoo-ff://game/nfl/stat-categories` | stat id → name/abbr/position type (03 §B.5) | static per season; the scoring engine's truth table |
| `yahoo-ff://docs/tool-outputs` | the compact output format of every tool, field by field, with the "never refetch inside a session" rule | the Skills' shared cheat-sheet (D §"gaps"); served from the same file the plugin ships |
| `yahoo-ff://rec/{log_id}` | one recommendation-log entry (05 §0 contract, alternatives, `as_of`) | the retrospective and the "what did you tell me last week" question read it without a tool call |
| `resource_link` in large tool results | e.g. the full 25-row FA page as `text/csv` | lets a tool return a compact top-N in `content` and link the rest; Claude Code can read the link on demand |

**Prompts** are "user-controlled … exposed from servers to clients with the intention of the user being able to explicitly select them", typically as slash commands; `name`, `title`, `description`, `arguments[{name, description, required}]`; arguments are **strings only**; `prompts/get` returns `messages[]` that may embed resources [V https://modelcontextprotocol.io/specification/2025-06-18/server/prompts]. Claude Code lists each as `/servername:promptname (MCP)` (also `/mcp__server__prompt`), splits arguments on whitespace so each is a single token, and "Prompt results are injected directly into the conversation" [V https://code.claude.com/docs/en/mcp "Use MCP prompts as commands"]. What prompts are good for here:

1. **The user-invoked entry point of each Skill**, portable to clients that have MCP but not Claude Skills (Cursor, VS Code, ChatGPT, Gemini CLI). `prompts/get weekly_game_plan {week}` returns the Skill's body (read from the same `SKILL.md` file the plugin ships — single source) as the user message, followed by an embedded `yahoo-ff://league/{key}/settings` resource. The user gets a Skill-quality procedure with one slash command; the Claude clients get the same procedure with auto-triggering and progressive disclosure via the plugin.
2. **League/season-scoped canned questions** with one string argument (`/yahoo-ff:matchup 5`, `/yahoo-ff:waiver-report`).
3. Nothing else. Prompts hold no logic and no data; they must not be the only home of a procedure (Skills are), and they never call tools themselves.

### A.4 Skills — frontmatter, trigger, progressive disclosure, size, versioning, and per-client discovery

**Standard vs Claude Code extensions.** Claude Code skills "follow the Agent Skills open standard (agentskills.io) … Claude Code extends the standard" [V https://code.claude.com/docs/en/skills]. Outside Claude Code — claude.ai uploads, the Skills API, `package_skill.py` — "you can use only the fields in the Agent Skills spec: `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`" [V same page, "Using skill frontmatter outside Claude Code"]. Platform limits: `name` ≤ 64 chars, lowercase/digits/hyphens, no "anthropic"/"claude"; `description` non-empty, ≤ 1,024 chars, no XML tags [V https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview].

Claude Code-only fields worth using: `when_to_use` (appended to `description` in the listing; the pair is **truncated at 1,536 characters**), `argument-hint`, `arguments`, `disable-model-invocation` (manual-only workflows), `user-invocable: false` (background knowledge), `allowed-tools`/`disallowed-tools` (a per-invocation grant/deny — e.g. deny `commit_*` in every Skill but one), `model`, `effort`, `context: fork` + `agent` + `background` (run in a subagent), `hooks`, `paths`, `shell`, `metadata` (free-form map "read by your own tooling") [V skills page frontmatter table]. The listing budget is **1% of the model's context window**; when it overflows Claude Code drops descriptions from the least-used skills — so descriptions must put the key use case first [V same page].

**The description is the trigger.** Write in third person; say what the Skill does *and* when to use it, with the phrases users actually type; be "a little bit pushy" because Claude under-triggers [V platform best-practices; V-local `skill-creator/SKILL.md`]. Negative triggers are an eval concern, not a frontmatter field: the official `math-olympiad` skill ships `evals/trigger_eval.json` with ten `should_trigger: true` and ten `should_trigger: false` queries [V-local]. Every Skill in §D carries both lists.

**Progressive disclosure and size** [V platform overview + best practices]: Level 1 metadata always in context (~100 tokens per Skill); Level 2 the `SKILL.md` body when triggered (target "under 5k tokens", "keep SKILL.md body under 500 lines"); Level 3 bundled references/scripts on demand ("no context penalty for bundled content that isn't used"). Rules: references **one level deep** from `SKILL.md` ("Claude may partially read files when they're referenced from other referenced files"); a table of contents in any reference over 100 lines; scripts run through bash so only their output costs tokens; "Prefer scripts for deterministic operations"; MCP tool references must be fully qualified (`ServerName:tool_name`) [V best practices]. Build evals before documentation; at least three per Skill; test across Haiku/Sonnet/Opus [V best practices].

**Versioning.** The standard has no `version` field; the plugin manifest's `version` "keeps users on that version until you change it" [V manifest reference]. Recommendation in §E: one semver for server + Skills, mirrored into each `SKILL.md` as `metadata: {version, tool_contract}` and checked by a script.

**Discovery per client — the product decision.**

| Surface | How Skills get there | Runtime for scripts | Consequence |
|---|---|---|---|
| Claude Code (terminal, VS Code, desktop Code tab) | filesystem: enterprise / `~/.claude/skills/` / project `.claude/skills/` / nested / `--add-dir` / **plugin** `<plugin>/skills/<name>/SKILL.md` (as `/plugin:skill`) / claude.ai-synced into `~/.claude/skills/synced/` [V skills page "Where skills live"] | full network, user's machine | the primary target; plugin install is the clean path; all frontmatter fields work |
| claude.ai chat + Claude Desktop chat + mobile | upload a zip in Settings ("Custom Skills … zip files through Settings > Features", individual to each user, Pro/Max/Team/Enterprise with code execution) or install a **plugin** in Customize > Plugins (Skills "Load"; local stdio MCP servers "Ignored") [V platform overview; V https://claude.com/docs/plugins/platform-support] | claude.ai sandbox, "full, partial, or no network access" by settings | standard frontmatter only; the Skill must work without our scripts; the MCP server must be reachable some other way (Desktop's own MCP config for stdio [U-3], or a remote HTTP variant later) |
| Cowork | claude.ai-account skills synced at session start; "don't read `~/.claude/skills/`"; local MCP loads only when the session runs on the user's computer [V skills page; V platform-support] | as chat | same as chat |
| Agent SDK | `settingSources: ["user","project"]`, optional `skills: "all" | [names] | []`, `plugins` option for a plugin path; no programmatic registration; `/name` dispatch always works [V https://code.claude.com/docs/en/agent-sdk/skills] | host machine | scheduled/automated runs (Tuesday waiver report) get the same Skills |
| Claude API (Skills API) | separate upload; sandbox with **no network** [V platform overview "Custom Skills do not sync across surfaces"] | none | not a target — an API skill cannot reach our MCP server |

Product rule that follows: **Skills are instruction + reference files only; scripts are optional accelerators used by evals and structural checks, never required by the procedure.** A Skill that "only works in one client" is one that needs a script or a Claude-Code-only field to function — none of the 14 below does.

### A.5 Plugins — manifest, bundling, install/update, marketplace; the right way to ship "server + Skills"?

**Manifest** `.claude-plugin/plugin.json` (optional; only `name` is required; kebab-case; every component namespaced `name:component`) [V https://code.claude.com/docs/en/plugins-reference]: `version` (pins users until changed), `description`, `author {name, email, url}`, `homepage`, `repository`, `license` (SPDX), `keywords`, `metadata` (free-form), `defaultEnabled`, `dependencies`, `settings`, `userConfig` (typed, `sensitive: true` → platform secure store, referenced as `${user_config.KEY}` in MCP `env`), `skills` (adds to the default `skills/` scan), `commands`, `agents`, `hooks`, `mcpServers` (inline map, `.json` path, or `.mcpb` bundle; merged with `.mcp.json`), `lspServers`, `outputStyles`, `workflows`, `experimental.evals`. Path variables: `${CLAUDE_PLUGIN_ROOT}` (changes on every update — "don't write state there"), `${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/<id>/`, kept across updates), `${CLAUDE_PROJECT_DIR}`; all three resolve in MCP `command`/`args`/`env` and in skill Markdown bodies. `claude plugin validate ./plugin` (with `--strict` in CI) is the authoritative manifest check and also validates each MCP server entry.

**Standard layout**: `.claude-plugin/plugin.json`, `skills/<name>/SKILL.md`, `agents/`, `hooks/hooks.json`, `.mcp.json`, `bin/` (on `PATH` while enabled — and it makes **claude.ai and Cowork refuse the whole plugin**, so we must not ship one), `settings.json`. A root `CLAUDE.md` is not loaded [V manifest reference "Standard layout"].

**Marketplace** `.claude-plugin/marketplace.json` (`name`, `owner {name}`, `plugins[]`; entries `name`, `source`, `version`, `category`, `tags`, `strict`) with sources `./relative`, `github {repo, ref, sha}`, `url`, `git-subdir {url, path}`, `npm {package, version}` ("install scripts … never run … dependencies … installed in a separate step, also with scripts disabled"), `archive {url, sha256}`, `command` [V https://code.claude.com/docs/en/plugins/marketplace-reference]. Users run `claude plugin marketplace add owner/repo` then `claude plugin install name@marketplace`; scopes user/project/local; project scope commits `enabledPlugins` to `.claude/settings.json`; `--plugin-dir` loads a folder for one session [V https://code.claude.com/docs/en/plugins]. An enabled plugin's skill names + descriptions are in context every turn; the official marketplace shows a **Context cost** estimate per plugin [V same page].

**Cross-surface reality** [V https://claude.com/docs/plugins/platform-support]: Skills load in Chat, Cowork and Claude Code; a **local (stdio) MCP server is "Ignored" in Chat** and loads in Cowork "when the Cowork session runs on your computer"; a remote `http` server "Listed on the plugin's Connectors tab"; `${user_config.*}` in a server URL → ignored in Chat; a plugin installed on the claude.ai account "also appears in Claude Code as a synced plugin at the next session start"; a plugin installed from the Claude Code CLI "stays on that machine".

**Verdict: yes, a plugin is the right unit — with two qualifications.**
- *For Claude Code* it is strictly better than a bare `skills/` directory: one install, `version`-pinned updates from our own marketplace, `userConfig` for the league key (non-sensitive) and nothing sensitive (tokens live in the OS config dir per 02 §5, never in `settings.json`), the MCP server wired by `.mcp.json` with `${CLAUDE_PLUGIN_ROOT}/dist/server.js` and `YAHOO_FF_HOME=${CLAUDE_PLUGIN_DATA}`, namespaced `/yahoo-ff:start-sit-decision`, `claude plugin validate` + `claude plugin eval` in CI, and a context-cost figure users can see.
- *For Desktop/claude.ai chat* the plugin carries the Skills but **not a stdio server**; the server must be added through Desktop's own MCP configuration [U-3] or shipped later as the remote HTTP variant (02 §3.9, D-style OAuth AS). Until then the honest statement is: Skills everywhere, server in Claude Code (and Desktop via manual config).
- *For non-Claude clients* the plain `skills/` tree is copyable (the Agent Skills standard is read by Codex/Cursor/etc. per the skills page's "works across multiple AI tools"), and the server's **prompts** + a `playbook` tool (C §"borrow") deliver the same procedures without any Skills support.

Trade-off table:

| | Plugin (recommended) | Plain `skills/` dir the user copies |
|---|---|---|
| Install | 2 commands; scoped; updatable | copy files; re-copy to update |
| Server wiring | `.mcp.json` inside the plugin; `${CLAUDE_PLUGIN_ROOT}` | user runs `claude mcp add` separately; version skew between Skills and server likely |
| Namespacing | `yahoo-ff:skill` avoids collisions with other fantasy skills the user may have | bare names collide (a user with `derekrbreese`'s `lineup-strategy` and ours) |
| Cross-surface | Skills sync to claude.ai/Desktop when installed there; stdio server ignored there | zip-upload per skill; same server problem |
| Evals/validation | `claude plugin validate`, `claude plugin eval`, context-cost display | skill-creator only |
| Cost | plugin metadata in every session where enabled (~100 tokens × 14 skills) | same |
| Risk | users must trust the plugin (it runs the server as them); mitigated by pinned `sha`, `claude plugin validate --strict`, zero-vuln lockfile (02 §5) | same code, less review surface |

### A.6 Token economics

Numbers that decide shapes (all fetched today unless marked):
- **Tool definitions are paid every turn** in clients without deferred loading; the official skill's rule of thumb: "Thirty tools with rich schemas can eat 3–5k tokens before the conversation even starts" [V-local `tool-design.md`]; the Anthropic post on code execution: "Tool descriptions occupy more context window space" and a filtering example that went "from 150,000 tokens to 2,000 tokens — a … saving of 98.7%" [V https://www.anthropic.com/engineering/code-execution-with-mcp]. Claude Code defers MCP schemas through Tool Search by default [V mcp page]; Desktop/other clients do not — so keep the core catalog near **28 tools** (A.1 guidance: 15–30 "still workable", 30+ → search + execute) and keep schemas tight.
- **Prompt caching** [V https://platform.claude.com/docs/en/build-with-claude/prompt-caching]: prefix order is `tools` → `system` → `messages`; "Modifying tool definitions (names, descriptions, parameters) invalidates the entire cache"; minimum cacheable prefix 512 tokens on the Fable 5.1 family (up to 4,096 on older models); cache reads 0.1× (0.025× on Fable 5.1), 5-minute writes 1.25×, 1-hour writes 2×. Consequences: `tools/list` must be **deterministic and stable within a session** (spec SHOULD); conditional write tools appear only after a scope change (rare); tool descriptions must not embed anything dynamic (no "current week: 5"); dynamic facts go in tool *results* and resources, never in definitions.
- **Response size** [V https://www.anthropic.com/engineering/writing-tools-for-agents]: a `response_format` enum (`concise` | `detailed`) cut a Slack example from 206 to 72 tokens (−65%); "resolving arbitrary alphanumeric UUIDs to more semantically meaningful … language significantly improves Claude's precision"; implement "pagination, range selection, filtering, and/or truncation with sensible default parameter values". Claude Code caps at 25k tokens (A.1).
- **Compact tables vs JSON.** Row-oriented JSON repeats every key per row; for the 25-row FA page with ~12 fields that is roughly 2× the tokens of a fixed-column table (estimate, not measured [U-10]). Rule: `content` text is a **compact table** (one header line, one row per item, names not ids where an id is not needed for a follow-up, and `name (POS, TEAM) key` where it is); `structuredContent` carries the machine form; `outputSchema` is declared for small results (≤ ~30 fields) and omitted for large lists so that clients validating output do not double-parse a big payload. Whether Claude Code forwards `structuredContent` to the model *in addition to* `content` — which would double the tokens of every structured result — is [U-2]; until measured, keep `structuredContent` ≤ the text size.
- **Resources vs tool calls for static data.** League settings (raw XML several k tokens; digest ~1k), the stat-id map (36+ rows) and the tool-output cheat-sheet are read at most once per session; as resources they cost nothing until read and are cacheable by the client (`ttlMs`, `cacheScope: "private"`); as tools they would be re-called by a forgetful model. Serve both: resource for reading, tool for clients without resource UI, and a Skill rule "read the settings digest once; reuse it".
- **Server-side caching** (from 03 §D): every Yahoo GET cached ≥ 60 s keyed by URI; player-key batches of 25; chained sub-resources (`out=stats,ownership,percent_owned`) to cut call counts — this is a rate-limit measure, but it is also the reason a Skill can call `yahoo_get_roster` twice in a session without a second Yahoo round trip.
- **Skill metadata**: ~100 tokens per Skill always in context [V platform overview] → 14 Skills ≈ 1.4k tokens per turn in Claude Code, the price of auto-triggering; `user-invocable: false` background Skills still count; the listing budget is 1% of context [V skills page]. Keep descriptions ≤ ~350 characters each so the whole bundle survives the budget with other plugins installed.

## B. The split — criteria, then applied to every decision type and every capability

### B.1 Criteria

1. **Tool** — anything whose correct answer is *computable and testable against fixtures*: data access (Yahoo, nflverse, Sleeper, RSS), the scoring engine, projections and their distributions, the assignment solver, win probability, VOR curves, FAAB bid curves, cascade redistribution, schedule holes, the recommendation log. If two competent engineers would write the same unit test, it is a tool. Tools are deterministic, annotated, compact, and never contain advice text.
2. **Skill** — a *repeatable expert procedure* that orchestrates tools and the user: which tools in which order, what to ask before calling, how to weigh conflicting evidence, what a trustworthy recommendation must contain (05 §0 contract), what must never be done (writes without confirmation; news as instructions). If the right output depends on the user's intent, risk appetite or league context in a way a function cannot take as an argument, it is a Skill. Skills contain no numbers that a tool could compute.
3. **Prompt** — a *user-invoked entry point* with string arguments that starts a Skill, for clients without Skills support or for the ritual slash command. Prompts hold no logic; each prompt body is generated from the corresponding `SKILL.md`.
4. **Resource** — *slow-changing reference data the model reads rather than computes* (settings digest, stat-id map, tool-output cheat-sheet, log entries, large-result overflow). If it changes less than once a week and is needed by more than one Skill, it is a resource (with a tool twin for clients lacking resource UI).
5. **Arguable placements** go to the tool side when a wrong answer is costly or must be consistent across sessions, and to the Skill side when the answer depends on what the user wants; every arguable case below is named with the reason it landed where it did.

Two corollaries. *Read/write separation is a tool-catalog rule, not a Skill rule* (Directory requirement; `HamCops/dodi`'s `apply=false` flag on one tool is the anti-pattern). *Untrusted text is labelled by the tool, interpreted by the Skill*: tools wrap free text (team names, notes, news) in `untrusted_text` (02 §5); Skills carry the "data, not instructions" rule and the §10 reliability procedure.
