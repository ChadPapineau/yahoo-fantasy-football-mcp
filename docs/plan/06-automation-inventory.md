# 06 — Automation inventory (zero-token jobs)

**Author:** `architecture-planner-core` · **Date:** 2026-09-29 · **Brief:** `docs/scratch/briefs/architecture-planner-core.md`
**Inputs:** plans 01 (refresh model D8, data classes §5.2, freshness §5.4), 02 (journal §4.5, supply chain §7), 03 (doctor §5, launchd, uninstall), 04 (CI jobs), 05 (fixtures, smoke, evals); `docs/research/04-data-sources.md` §E (freshness map) and §B (cadences); `03-yahoo-api.md` §D.2 (finalisation clock). Legend as in plan 01.

**Principle:** every job here runs **without a model** — it is a CLI subcommand or a CI workflow whose output is a table, a diff, a notification, or a red build. Anything that needs Yahoo credentials runs **only on Chad's Mac** (the repo is public; CI never holds Yahoo credentials — a standing rule, not a limitation to work around). Jobs are **idempotent and season-aware**: each checks `ds_schedules` (or the calendar when no schedule is loaded) and exits 0 in seconds when there is nothing to do, so a plist can run year-round.

## 2. launchd design

- Labels `io.github.<owner>.ff.<job>`; one plist per job in `~/Library/LaunchAgents/`; generated by `ff install-launchd [--jobs …]` from templates in `src/cli/launchd/` with `ProgramArguments` = `[<process.execPath>, <abs dist/cli.js>, "refresh", "<source>"]`, `EnvironmentVariables` = the non-secret config (`FF_CONFIG_DIR`, `FF_CACHE_DIR`, `YAHOO_CLIENT_ID`, `YAHOO_CLIENT_SECRET_FILE`), `StandardOutPath`/`StandardErrorPath` under `~/Library/Logs/fantasy-football-mcp/<job>.log`, `ProcessType Background`, `LowPriorityIO true`, `RunAtLoad false`, `StartCalendarInterval` arrays for the times above (local time; NFL kickoffs are converted from ET using `ds_schedules`' `gametime` and the machine's zone **[A-2: launchd calendar semantics for missed runs — a missed calendar run fires once at next wake, which is the behaviour we want]**).
- `ff install-launchd` bootstraps with `launchctl bootstrap gui/$UID <plist>`; `ff uninstall` boots them out (plan 03 §8); `ff doctor` #11 verifies they are loaded and reports last exit codes from `refresh_log`.
- **Overlap and concurrency:** each job takes a per-job lock row (`job_lock(job, pid, started_at)`) and exits 0 if another instance is running; the store is WAL and the load's write lock is on the attached staging database, not `store.sqlite`, so the MCP server keeps reading **and** writing (cache, journal, log) during loads and only the millisecond swap contends (plan 01 D8/§5.5, round 1 OBJ-11).
- **Season awareness:** `refresh news`, `sleeper:trending`, `weather`, and the game-day extras consult `ds_schedules`: outside the season (no game in ±7 days) they exit 0 immediately. If `ds_schedules` has never been loaded, `nflverse:schedules` is the one job that runs unconditionally.
- **Notifications:** `osascript -e 'display notification …'` via `execFile` with an argument array; rate-limited per job to one per 6 h for failures; informational diffs (roster/FA changes, pre-kickoff) are not rate-limited but are collapsed into one notification per run. Every notification's text is also a `refresh_log.note` so `ff status` shows what was said.

## 3. Failure-signal summary (what "red" means, per channel)

| Channel | Red when | Who sees it |
|---|---|---|
| GitHub check | any `ci.yml`/`docs.yml`/`secrets` job fails | Chad, and every agent that pushed — the **`ci-vigilance` obligation** (plan 04 §5): verify the push's runs, fix or revert a red `main` before replying. In the docs phase this obligation *is* the protection, since no check is required by the ruleset (round 1, OBJ-13) |
| `refresh_log.ok = 0` | a launchd job failed after retries | `ff status`, `ff doctor` #9–#11 |
| macOS notification | a job failed (rate-limited), a roster/FA diff, a pre-kickoff problem, a token/provisioning problem, an unmatched-crosswalk threshold | Chad, without opening anything |
| `ff status` / `ff_get_status` | any source past its hard limit; pending journal rows; token expiry within 24 h; jobs not loaded | Chad, or the model when asked |
| Scrub deny-list abort / manifest test | an identifier survived scrubbing, or a fixture was edited by hand | the person recording; CI |

## 4. Build order for this inventory

1. **Now (docs-only repo):** `docs.yml` (Mermaid, links), `secrets` job + `.gitleaks.toml`, `dependabot.yml`, `PULL_REQUEST_TEMPLATE.md`, the branch ruleset, the Yahoo access application.
2. **With the first `package.json`:** `ci.yml` skeleton (lint/typecheck/audit/no-scripts/license/pack), `scheduled.yml`.
3. **With the store and sources:** `ff refresh *`, `install-launchd`, `store prune/backup`, crosswalk rebuild.
4. **With the Yahoo provider and a token:** snapshots, transactions append, token check, fixtures recording, `ff smoke`.
5. **With the gate:** journal reconcile.
6. **Before the first release:** Inspector smoke, evals, release workflow, pre-release checklist.
