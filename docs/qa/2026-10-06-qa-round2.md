## Details of every confirmed finding

### QA-2-001 — The synced-folder refusal names four folders; the guard refuses seven and every `~/OneDrive*`

- **Severity** low · **area** config · **category** ux · **source** the git-tree guard hand-off (its
  "fix now" part)
- **Files** `src/config/paths.ts`
- **What** `REFUSAL_TEXT.synced_folder` was "path is inside a cloud-synced folder (Documents,
  Desktop, iCloud Drive, CloudStorage); use ~/.config or ~/.cache". Since `322f8fd` (QA-1-044/067)
  the guard (`syncedFolders`) has also refused `~/Dropbox`, `~/Google Drive`, `~/OneDrive` and a
  business `~/OneDrive - <organisation>`. A config, cache or league-file path in one of those was
  refused with a message that does not name the folder it was refused for.
- **Expected** The refusal is the only remedy text the user gets, so it names every folder the guard
  refuses. The guard and the message read one list, so a folder added to one is in both.
- **Actual** `FF_CONFIG_DIR=~/Dropbox/ff` (or `~/Google Drive/…`, `~/OneDrive…/…`) was refused with
  the four-folder message above.
- **Status** fixed — commit `8852df5` (one `SYNCED_FOLDERS` list read by the guard and by the
  message, which now names each folder as `~/<folder>`, a prefix as `~/OneDrive*`) · test:
  tests/config/paths.test.ts "a refusal names the folder it refused, for every folder the guard
  refuses [QA-2-001]" (walks `syncedFolders()` with a business OneDrive present) · mutation-checked
  (fix reverted: that test fails)

### QA-2-002 — The onboard Skill and its guide say the server does not look for `~/Dropbox`; it has refused it since `322f8fd`

- **Severity** low · **area** skills · **category** spec · **source** the git-tree guard hand-off
  (its "fix now" part)
- **Files** `skills/onboard/SKILL.md`, `skills/onboard/references/onboard-league-yaml.md`
- **What** SKILL.md §3 and the guide's "Saving it" said the server refuses only this checkout,
  `~/Documents`, `~/Desktop`, iCloud Drive and `~/Library/CloudStorage`, and "does not look for …
  folders such as `~/Dropbox`". That has been false since `322f8fd`. The QA-1-044/067 test checks
  only over-claims (a location the text says is refused must be refused), so it could not see an
  under-claim.
- **Expected** Where the text says what the server refuses, it names every folder the server refuses
  (this checkout and every synced folder in the home folder), and it still says the server does not
  look for other git working trees.
- **Actual** Both texts left out `~/Dropbox`, `~/Google Drive`, `~/OneDrive` and
  `~/OneDrive - <organisation>` (8 omissions across the two files).
- **Status** fixed — commit `3469278` (both texts list the seven folders and the business OneDrive)
  · test: tests/skills/onboard-location-claims.test.ts "every folder the server refuses is named where
  the text says what it refuses [QA-2-002]" (the under-claim check, beside the existing over-claim
  check; the folder list comes from the guard itself) · mutation-checked (fix reverted: that test
  fails, naming the 8 omissions)

### QA-2-004 — `hold_vs_stream` can describe another position than `rec`, with nothing saying which

- **Severity** medium · **area** analytics · **category** correctness · **source** the E5
  per-position hand-off
- **Files** `src/domain/analytics/kdef.ts`, `src/domain/analytics/types.ts`,
  `src/mcp/tools/analytics.ts`, `skills/*/references/tool-outputs.md`
- **What** `ff_analyze_waivers` returns one `hold_vs_stream`, taken from the requested position
  whose best option gains most over its starter. That can be a position whose starter is locked,
  which `rec` skips. In the default call (`positions` = K and DEF) the numbers could belong to one
  position and `rec` to the other, and the result did not say which position the numbers describe.
  The Skill and the `ff.stream` prompt have ranked one position per call since QA-1-063, so they
  were not affected; a direct call with both positions was.
- **Expected** The result says which position `hold_vs_stream` describes, and those numbers equal
  that position's own single-position call.
- **Actual** On a Friday with my kicker locked (his game was on Thursday), a K-and-DEF call returned
  `rec.action` about DEF and `hold_vs_stream` = `{ streamability, current_starter_delta }` holding
  the kicker's numbers, with no position field.
- **Status** fixed — commit `0d210f4` (an additive `position` in the domain type, the strict output
  schema and the tool-outputs cheat-sheet in every Skill; the advertised `outputSchema` lists only
  `data`'s top-level names, so `tools/list` is unchanged) · tests: tests/domain/analytics/kdef.test.ts
  describe "QA-2-004" (a two-position call labels it, with numbers equal to that position's own call,
  and both positions reached; a one-position call is labelled with that position),
  tests/domain/analytics/kdef-locks.test.ts "Friday, K and DEF in one call: the locked kicker's numbers
  say K while rec is about DEF", tests/mcp/e5-hold-position.test.ts (the served default call passes the
  strict schema with the label) · mutation-checked (fix reverted: all 5 QA-2-004 tests fail)

### QA-2-005 — stream-kdef presents `marginal_value` p10/p90 as the range of the gain over the current starter

- **Severity** low · **area** skills · **category** correctness · **source** the E5 per-candidate
  hand-off
- **Files** `skills/stream-kdef/SKILL.md`, `skills/stream-kdef/evals/cases.json`
- **What** The Skill printed `marginal_value.p10`/`p50`/`p90` as "gain over your current
  kicker/defense". That interval is the candidate's own spread shifted by the starter's mean. It
  leaves out the starter's own variance, so it is not the interval the verdict was decided on
  (`rec.delta_vs_next`).
- **Expected** The gain's range is the verdict's interval: `rec.delta_vs_next.p10` to `.p90`, with
  the signs flipped for a hold. `marginal_value` is shown by its mean only (plan 09 §2: the Skill
  never re-derives a number the tool did not decide on).
- **Actual** On the fixture league: kicker −4.2 to 12.9 presented, against the verdict's −6.8 to
  15.1; defense −2.5 to 9.5, against −4.9 to 11.4.
- **Status** fixed — commit `ebe095b` (the Skill gives `marginal_value.mean` as the expected gain and
  takes the range from `rec.delta_vs_next`; KD-1 gains a matching rubric) · test:
  tests/skills/stream-kdef-contract.test.ts describe "QA-2-005" ("marginal_value is shown by its mean
  only"; "every gain range presented equals the interval the verdict was decided on", replaying the
  Skill's tool sequence on the fixture league) · mutation-checked (fix reverted: both tests fail)

Related documentation fix, not a finding: `5302d5c` corrects the README Skill table and plan 09 §3.4,
which still showed one `ff_analyze_waivers(positions: [K, DEF])` call for stream-kdef.
